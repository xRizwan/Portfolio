<h2 id="brief">The brief</h2>

The bank in the project runs its fraud checks as a batch job, so a bad transaction is only noticed hours later. The new system has to analyse up to 1,000 transactions per second, show the high-risk ones to fraud analysts right away, and keep every transaction so it can be replayed for compliance.

I did not build this system. The project was to design it and defend the design in a document, which is linked at the bottom.

<Callout>
  <strong>This is a design, not a running system.</strong> The numbers on this page are requirements
  from the brief and targets I proposed. I have not measured any of them.
</Callout>

<h2 id="flow">One transaction, three stages</h2>

The easiest way to explain the design is to follow one transaction through it.

<FlowExplorer />

1. **Accept.** The API Gateway checks who is calling. The Transaction Service validates the transaction, saves it in PostgreSQL, publishes a `TransactionReceived` event to Kafka, and returns a transaction ID.
2. **Analyse.** The Fraud Detection Service reads the event, looks up recent customer features in Redis, runs the model, and publishes `FraudAnalysisCompleted` with the risk score and the model version.
3. **Deliver.** Three services read that result on their own. The Alert Service pushes high-risk results to analysts over a WebSocket. The Reporting Service stores results so analysts can search them. An archive consumer copies every event to S3.

<h2 id="decisions">Why I split it this way</h2>

My first idea was simpler: the API calls the model and waits for the answer. The problem is that the API is then only as fast as the model. If the model slows down, the bank stops accepting transactions.

So I put Kafka in the middle. The API only has to save the transaction and publish an event, and it can answer straight away. The model does its work a moment later. The price is that for a short time a transaction is accepted but has no fraud result yet. I decided that was fine here, because the brief asks for fast alerts to analysts, not for blocking the payment.

Kafka also solved the replay requirement almost for free. It keeps the events, so a service that was down can continue from where it stopped, and the reporting database can be rebuilt by replaying them.

I left out a service mesh. The API Gateway, Kubernetes, and OpenTelemetry already cover routing, scaling, and monitoring for a system of this size.

<h2 id="failures">What happens when something fails?</h2>

This was the part I understood least when I started, and the part I learned the most from.

A consumer tells Kafka that an event is done only after it has finished processing it. If the service crashes just before that, another instance reads the same event again. So the same transaction can be processed twice. I first thought Kafka's exactly-once feature would fix this, but that only covers Kafka-to-Kafka steps. The database sits outside Kafka. The fix is to use the transaction ID or event ID as a unique key, so writing the same result a second time changes nothing.

The other protections in the design:

- An event that keeps failing is retried, then moved to a dead-letter topic so it does not block the rest.
- Kafka topics are replicated across brokers, and PostgreSQL has backups and point-in-time recovery.
- Redis is treated as a cache. If a feature is missing, the service uses a fallback value and records that it did.
- Alerts are stored, so an analyst whose WebSocket dropped can load the ones they missed over REST.

Every request and event carries a transaction ID and a trace ID. With OpenTelemetry that makes it possible to follow one transaction through the API, Kafka, Redis, the model, and the alert.
